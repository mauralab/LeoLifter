# LeoLifter Web

Responsive public landing page plus Telegram-linked sign-in and an authenticated account workspace. Workout-program screens and the Telegram Mini App are still future work. The public landing page makes no database calls.

## Run

```sh
npm install
npm run dev
```

Open http://127.0.0.1:3000. `/` redirects to `/en`.

## Languages

Localized, server-rendered routes: `/en` (English), `/uk` (Ukrainian), `/nb` (Norwegian Bokmål), `/de` (German), `/pl` (Polish). The header language picker navigates between them; the selected language is kept in the URL and survives refresh/sharing. Each page has the corresponding HTML language and metadata. Unknown locale paths return 404.

Translations live in `lib/i18n/messages/`, with a shared dictionary shape checked by TypeScript. Add new keys to every dictionary. Norwegian currently means Bokmål; Nynorsk can be added separately if needed. Translation copy should receive native-speaker review before public launch.

## Page structure

- `app/[locale]/layout.tsx`: localized document, metadata and static locale generation.
- `app/[locale]/page.tsx`: localized landing route.
- `components/landing/landing-page.tsx`: responsive introduction, local sample-workout interaction, platform vision and roadmap.
- `app/globals.css`: existing shadcn tokens plus scoped landing styles.
- `public/brand/leo-web.png`: original LeoWeb mascot used by the header/footer wordmark.
- `app/favicon.ico`: supplied Leo.ico browser-tab icon, automatically registered by Next.js.

The workout preview is sample data only. Day selection, exercise completion and reset work locally; refreshing resets the preview. All calls to action navigate to real page sections. Future capabilities are described as plans rather than presented as working account/program features. The header includes a light/dark toggle. It follows the system preference initially, saves an explicit choice locally, and keeps it across reloads and language changes. Flags accompany every language (UK for English); SVG artwork renders independently of operating-system emoji support. On narrow screens the trigger shows its flag while language names remain visible inside the keyboard-accessible menu.

## Future application direction

Users should be able to create and follow workout programs from the browser and a Telegram Mini App. Keep shared responsive components and locale dictionaries reusable by both entry points. LeoBot can now sign users into this web app with verified, short-lived links. The full Mini App and workout notifications remain future work; nickname/password sign-in with Telegram approval is implemented. Internal user IDs and linked Telegram IDs remain separate. Never treat raw URL IDs or usernames as proof of identity.

## Telegram authentication

`/[locale]/auth` is a blank hand-off page opened from a personal bot link. It verifies the ID, username, private chat ID, issue time, nonce and SHA-256 HMAC signature shared with LeoBot. Links expire after five minutes and are single-use. Initial GETs and Telegram link previews never consume a link or create an account: the actual browser submits a bounded, same-origin POST to `/api/auth/telegram`.

The server uses the existing PostgreSQL `users`, `user_telegram`, `user_profiles`, `user_settings` and `user_sessions` tables. New users get `nickname = tg_username`; when Telegram provides no username the fallback is `telegram_<id>`. Telegram ID is the account identity; usernames are never used to merge accounts. Existing nicknames/profile/preferences are preserved. Chat ID and the Telegram-to-user mapping are saved, and missing personal records are initialized.

Nonce consumption, sign-up/linking and session creation share one transaction. Concurrent sign-ups for one Telegram ID are serialized. A new `telegram_login_links` table records only hashed nonces; failed transactions do not consume links. Existing tables are not altered. This additive migration was applied to the existing local database during setup.

Authentication issues a 15-minute signed access JWT and a 30-day random refresh token. Cookies are HTTP-only, SameSite=Lax and Secure on HTTPS; refresh cookies are scoped to `/api/auth`. Only SHA-256 uppercase-hex refresh-token hashes are stored, matching LeoCore's format. The profile validates both the access token and the database session before displaying the account workspace. Missing/expired access cookies trigger a same-origin refresh POST; refresh tokens rotate atomically. `/api/auth/logout` revokes the session and clears cookies. Refresh expiry is fixed rather than extended indefinitely.

### Local setup

Ignored `.env.local` and `../LeoBot/appsettings.Local.json` were generated using the existing Rider database connection and fresh matching signing secrets. Do not commit either file. Restart the web app and LeoBot after configuration changes, then send `/start` for a new personal link.

For another checkout, copy `.env.example` to `.env.local` and supply:

```text
DATABASE_URL=<PostgreSQL URL for the existing LeoDatabase database>
APP_ORIGIN=http://127.0.0.1:3000
TELEGRAM_AUTH_SECRET=<random shared secret of at least 32 UTF-8 bytes>
SESSION_SECRET=<different random signing secret of at least 32 UTF-8 bytes>
```

Set LeoBot `Telegram__AuthLinkSecret` to exactly TELEGRAM_AUTH_SECRET and `Telegram__WebAuthUrl` to `APP_ORIGIN/en/auth`. Use HTTPS for a public deployment. HTTP is only accepted for loopback development. A phone opening localhost cannot reach the PC; use a public HTTPS address/tunnel and change both origins together for phone testing. The app origin must have no trailing slash.

Initialize the additive auth table once per database:

```sh
npm run db:auth:migrate
```

The Drizzle schema here maps a subset of existing EF Core tables for queries. Do not run blanket Drizzle push/generation against the shared database using this partial schema: EF Core remains the owner of the existing application schema.

Login URLs are bearer credentials: never share them or log complete query strings. Development auth request logging is disabled, referrers carry only an origin, and browser history loses the query on hand-off. Configure any production proxy/access logs to redact auth query strings too. Expired consumed-link rows can be deleted once their expiry has passed; signature expiry still prevents replay. No cleanup scheduler is enabled yet.

End-to-end validation used a separate PostgreSQL 18 cluster with the exact EF Core schema and a real browser: .NET-to-TypeScript signatures, new/returning users, Telegram mapping, cookie/session state, replay/tamper/expiry rejection, parallel sign-ups, missing usernames, refresh rotation, logout, and transaction rollback. Existing user records were not used as test data.

## Profile workspace

`/[locale]/profile` has four responsive sections, translated into English, Ukrainian, Norwegian Bokmål, German and Polish:

- **Profile:** nickname, birthday, sex, height/unit, two-letter country code, city and IANA time zone. Optional fields can be cleared. Height units default to the saved length preference (cm initially); clearing height also clears its stored unit, and an existing height retains its own unit when preferences change. The nickname/profile save is atomic.
- **Settings:** language, weight unit and length unit. Saving a language changes the profile URL to that locale; the header picker also keeps you on the current page.
- **Password:** set an initial password or change it after verifying the current password. New passwords require 12–128 characters and confirmation. Hashes use ASP.NET Identity V3 PBKDF2-SHA512, compatible with LeoCore; older Identity hashes can be verified too. Setting/changing a password revokes other sessions while keeping the current session. Nickname/password sign-in requires a second approval in Telegram; direct Telegram sign-in also remains available.
- **Sessions:** ten non-revoked records per page, with device label, sign-in/update/expiry timestamps, status and current-device marker. Revoke one session, sign out other sessions, or sign out the current device. Timestamps use the saved time zone, falling back to UTC. Session updates indicate token/security changes rather than general browsing activity.

The server page loads safe DTOs through `lib/profile/store.ts`. Client forms in `components/profile/profile-workspace.tsx` POST bounded URL-encoded data to `/api/profile`. Every mutation checks the request origin and verified active session, derives ownership from that identity, and locks/rechecks the user/session before writing. Session lists never expose token hashes. Existing database tables are mapped in Drizzle; no new migration is required for this feature.

Password operations are limited to five attempts per account per 15 minutes in each process. Use a shared limiter before scaling to multiple server processes. Validation and expected errors are localized; database exceptions and credentials are not sent to the client.

Validation used an isolated PostgreSQL fixture and browser automation for persistence, invalid/oversized/duplicate inputs, CSRF and anonymous rejection, password setup/change and .NET hash interoperability, cross-user session protection, pagination, individual/bulk/current-session revocation, and mobile layouts in all five languages. Production build, lint and type checks also pass.

### Refresh and local addresses

`proxy.ts` redirects local GET/HEAD page/auth visits from localhost or ::1 to the configured loopback APP_ORIGIN, keeping sign-in and refresh cookies on one host. `skipProxyUrlNormalize` preserves the absolute redirect because Next.js otherwise normalizes loopback IPs to localhost. POST origin checks remain strict; unrelated hosts and origins are never trusted through this convenience redirect.

Opening `/api/auth/refresh` in the browser now redirects to the localized profile, where the existing browser hand-off renews an expired/missing access cookie using POST. GET itself never rotates a token. A valid access cookie can open the profile immediately. Cookies originally created on a different host are not transferred; request a new bot sign-in link if no session exists on the configured host.

The landing header includes a localized profile link on desktop and mobile. Revoking a session removes it from the profile list/count/pagination while retaining its database record for history.

## Nickname/password sign-in with Telegram approval

Open `/{locale}/login` or use **Sign in** on the landing page. Enter a nickname, then the account password, then wait on the confirmation page. LeoBot sends a private **Is this you?** message with **Yes / No**, a request code matching the browser, device category and UTC request time. Yes signs in the initiating browser; No blocks only that attempt. Existing sessions are unaffected. Requests expire after five minutes and can be cancelled in the browser; reloading the waiting page resumes the same request.

Requirements: set a password from Profile, link the account to Telegram through the existing bot sign-in flow, keep LeoBot running, and configure its `ConnectionStrings__LeoDatabase` to the same PostgreSQL database used by LeoWeb. The ignored local bot configuration has been populated for this machine. The web app never needs the bot token or a public webhook. Restart both applications after updating.

`npm run db:auth:migrate` now applies the ordered, idempotent additive auth SQL files, including `0002_password_login_approval.sql` (already applied locally). It adds `password_login_requests` and `auth_rate_limits`; it does not alter application tables or impose a nickname uniqueness constraint. Expired request rows and old rate-limit buckets can be removed later; no cleanup schedule is enabled.

Nicknames are matched case-insensitively after trimming, and must resolve to exactly one account. Ambiguous nicknames, incorrect passwords, missing passwords and missing Telegram links use the same failure response. A user with an ambiguous nickname can enter via Telegram and change their nickname in Profile. There are ten credential attempts per normalized nickname per 15 minutes, enforced atomically in PostgreSQL across processes. Apply edge/network abuse limits as part of public deployment too.

`lib/auth/password-login.ts` verifies Identity-compatible hashes, persists a request after successful verification, and redeems an approved request once. A 256-bit browser secret is kept in an HTTP-only, SameSite=Strict cookie scoped to `/api/auth/password`; only its hash is stored. Knowing the request ID or seeing its reference code is insufficient to redeem it. No access/refresh tokens are issued before approval. Redemption rechecks the credential fingerprint and Telegram mapping and creates the normal 15-minute access / 30-day refresh session in one transaction. Password or Telegram-link changes invalidate outstanding approvals.

`POST /api/auth/password` starts a request; `POST /api/auth/password/status` polls/redeems it or cancels with `action=cancel`. Both enforce trusted origin and bounded form inputs. No state-changing GET endpoint exists. The status response never exposes passwords, stored hashes or refresh tokens. Missing/expired refresh sessions now lead to the login page; `/start` sign-in remains available.

LeoBot's `PasswordApprovalWorker` claims pending notifications with a short retry lease (`FOR UPDATE SKIP LOCKED`), sends localized buttons, and records Telegram's message ID. Callback decisions require the stored Telegram sender, private chat, message ID, pending state and unexpired request; replay cannot change a decision. Sending errors use sanitized logs and never bypass approval. Delivery retries are bounded; if delivery fails or the bot is offline, the attempt eventually expires.

Validation used isolated PostgreSQL, browser automation and a stub Telegram HTTP transport, including both decisions, expiration, cancellation, replays, wrong sender/chat/message, group callbacks, another browser's forged proof, concurrent redemption, password-change invalidation, ambiguous names, CSRF, database-backed throttling and responsive layouts in all five locales. No real Telegram messages were sent during tests.

## Exercise management

`/[locale]/exercises` reads the shared PostgreSQL catalog, searches default and translated text, filters by exercise type and paginates cards (12 per page). Requested-language text falls back to English and then the default exercise fields. The catalog is public; create/edit pages and POST/PUT/DELETE endpoints require an active signed-in session. All signed-in users can modify exercises; roles are intentionally not checked yet. Mutations enforce the configured APP_ORIGIN.

The original card layout, search box and filter chips are retained. The editor retains its language sidebar, drag-and-drop cover upload, live preview and preview dialog. Additional media fields are expandable.

Create opens `/[locale]/exercises/create`; selecting a card opens `/[locale]/exercises/[id]`. Edit default title/description, type, body/additional-weight flags, translations, and ordered image/video entries. Each media entry has independent URL, title, description and alternative text per language. Languages come from the database. Save replaces translations and media atomically; media row IDs are internal and are regenerated. Delete asks for confirmation and refuses exercises referenced by programs or workouts.

Uploads accept PNG/JPEG/WebP up to 5 MB and MP4/WebM up to 25 MB, with file signatures checked. Files are stored outside Git under `.exercise-media` by default; set `EXERCISE_MEDIA_ROOT` to an absolute durable directory in production, back it up separately and use shared storage if running multiple web instances. `/api/exercises/files/[name]` serves files with byte-range support. External HTTP(S) media URLs are also supported. Removing media removes its database references; uploaded files are retained so reused URLs remain valid. Unused uploads require periodic storage maintenance. Files are public, like the exercise catalog.

Server validation limits lengths/counts and rejects unknown or duplicate languages. Catalog presentation lives in `components/exercises`, database transactions in `lib/exercises/store.ts`, and request/upload handlers under `app/api/exercises`. Frontend interface copy supports the five application locales; API failure details currently use English.

## Program editor canvas

`/[locale]/programs` opens the Programs workspace. Create program leads to `/[locale]/programs/create`, with a program-name field and dotted canvas. Drag Cycle or Day from the palette, or click/press Enter to add a block. Cycle and day names are editable on each block. Drag a day into a cycle to assign it; move the cycle by its grip to carry its days. Days must belong to a cycle; drops on the background are rejected, preserving any existing membership. Days fill the cycle content height and arrange horizontally. Nested cycles fill the parent content width and stack vertically; containers grow to fit. Existing blocks can be reordered by dropping them before/after siblings, or with arrow keys on their grips. Cycles cannot be nested into themselves or their descendants. Removing a nonempty cycle asks for confirmation and removes its subtree, so no days become orphaned.

Clicking a cycle or day opens its options panel (on the right on desktop, below the canvas on smaller screens). Cycles expose title, description, repeat count, parent cycle and sibling position; days expose title, parent cycle and sibling position. Groups, exercise assignments and set targets have their own contextual options. Changes update immediately in the local draft. Repeat counts are positive integers, parent choices exclude the selected cycle and its descendants, and days cannot become root items. Day columns have a 240 px minimum width in canvas coordinates at 100% zoom; cycles expand to fit additional days.

The canvas supports background dragging to pan, scrollbars, 50–150% zoom, an 8-pixel positioning grid and arrow-key movement on focused grips (Shift for larger steps). Touch devices support the palette and grips, with click-to-add as an alternative. Cycle containers automatically grow with their contents. Root canvas coordinates are saved as editor metadata; normalized sibling positions remain the database ordering.

`components/programs/program-workspace.tsx` owns the draft and save status; `program-canvas.tsx` manages selection, dragging and zoom. Save program persists the draft to PostgreSQL and switches a new draft to its edit URL. Unsaved changes remain local. Save as downloads a separate file snapshot. The interface supports all five application languages.

### Groups, exercises and set targets

The program palette supports the complete draft tree: Cycle → Day → Group → Exercise → Set. Groups stack inside days and expose a name and repeat count. Exercise blocks stack inside groups and select an existing catalog exercise through a searchable picker. Set targets stack inside an exercise and expose optional paired repetition bounds and paired numeric bounds plus a unit (`kg`, `lb`, `percent_1rm`, `km`, `mi`, `s`). Invalid/incomplete ranges remain editable drafts and show an error; value bounds support up to three decimal places, matching numeric(12,3).

In database terms, an Exercise block represents `program_day_sets` (the exercise assignment) and each UI Set represents a target template for one or more `program_set_exercises` rows. `setCount` is an editor quantity (default 1); saving expands it into individual target rows. Parent types are enforced for drag/drop, palette clicks and the inspector. Parent and position controls preserve descendants when moving branches; removing a nonempty branch requires confirmation. Containers expand to fit all nested content.

The create route reads the public localized exercise catalog from the existing database. Signed-in users can save their program structure, ranges and layout and reopen their own programs from the Programs list. Catalog changes remain in the separate exercise library.

### Clipboard, identical sets and exercise picker

Select an object and use the canvas toolbar or Ctrl/Cmd+C, Ctrl/Cmd+V and Ctrl/Cmd+D to copy, paste or duplicate. The editor clipboard takes a snapshot of the complete branch, preserving order and targets while assigning fresh IDs on every paste. Select a compatible destination parent to paste into a different branch; pasting alongside the same kind creates a sibling. Root cycles paste with a position offset. Inputs keep their native text shortcuts. This clipboard is local to the current editor page and is cleared on navigation/reload.

An exercise's options include **Identical sets**: choose 1–100 sets and one optional repetition/value range, then apply. This creates one compact target object with `setCount`, retaining the first existing object ID when possible. Replacing differing targets asks for confirmation. Edit the quantity in its inspector; quantities above one show an ×N badge, and the exercise header shows the total number of physical sets. Separate set objects remain independent; copy/paste preserves their quantities.

Exercise selection opens a keyboard-accessible popup from the exercise card or its inspector button. It supports text search, type filters (repetitions/distance/duration), weight filters (body weight/additional/no additional weight), clear filters and 12-result pages. The picker reads localized descriptions and weight flags from the existing public catalog. Selecting a different catalog exercise preserves its draft set targets.

### Save as text or Excel

The canvas toolbar's Save as dialog downloads the current draft as UTF-8 `.txt` or a real `.xlsx` workbook, with an editable file name. Text includes a readable hierarchy and a versioned JSON snapshot of all draft blocks. Excel includes a styled localized Program report (quantities, repeats, target ranges, units and descriptions) and a Draft data sheet with IDs, parents, positions, coordinates and raw target fields. Numeric report values are typed numbers; text, including names beginning with `=`, remains text.

ExcelJS loads dynamically only when an Excel export is requested. Downloads are generated in the browser independently of database saving, without sending draft data to an export service. Files can be opened in text editors/Excel; importing them back into the editor is not implemented yet.

### Database saving

Apply `npm run db:programs:migrate` once per database (safe to repeat). The additive SQL in `LeoDatabase/Sql/0002_program_editor_layout.sql` creates `program_editor_layouts`; existing training tables and records are preserved. This web-only metadata table stores day titles, root coordinates, stable canvas IDs and compact target-row groupings. Training data remains in `programs`, `program_cycles`, `program_days`, `program_day_groups`, `program_day_sets` and `program_set_exercises`, so LeoCore can continue using the same models.

Authenticated `POST /api/programs` creates a private program owned by the current user; `PUT /api/programs/[id]` updates that user's program. Both require a matching Origin, enforce input/size/hierarchy limits and use one transaction. A program-root row lock follows LeoCore's locking protocol; a content revision rejects stale browser saves, including changes made through the console. Existing rows are updated and reparented before removed rows are deleted. Reorders retain day IDs and their workout references; deleting a day intentionally follows the existing database foreign-key behavior. A missing exercise rolls back the entire save.

`lib/programs/store.ts` reads the normalized graph on every load, using editor metadata only for presentation. If console edits change a member of a compact set batch, different targets reopen as separate objects. `/{locale}/programs/[id]/edit` loads an owned program; the Programs list shows owned programs in pages of 12. New programs require a name, cycles require names, and exercise assignments require a catalog choice. Limits are 1,000 canvas objects and 5,000 expanded target rows per program. Save errors retain the local draft; a conflicting revision requires reopening the current database version.

### Program list, fixed counts and ranges

Programs contains **My programs**, a searchable list of the signed-in user's saved programs with 12 cards per page. Clicking a card reopens its editor. Expired access cookies now use the existing refresh-session handoff and return to Programs instead of showing an empty list. Saving refreshes the route data so returning to the list includes the new program.

In set options and Identical sets, choose Single number (e.g. 3) or Range (e.g. 3–5). Repetitions have the same choice: 10 stores equal `target_reps_min`/`target_reps_max`, while 8–12 stores separate bounds. Set counts stay in the options panel; badges, copied branches and text/Excel exports preserve ranges. Range minimum may be zero for a fully optional set batch; maximum is 1–100 and cannot be lower than the minimum.

`npm run db:programs:migrate` now also applies `LeoDatabase/Sql/0003_optional_program_sets.sql`. It adds `program_set_exercises.is_optional` with default false, preserving all existing rows as required sets. A 3–5 batch writes five physical target rows: the first three required, the last two optional. The canvas uses `setCountMin` for the minimum and existing `setCount` for the maximum; older payloads without a minimum remain fixed counts. Loading derives both bounds from the normalized rows, while layout metadata groups matching, consecutive target rows. Required rows must precede optional rows to collapse a batch; independently modified rows reopen separately. LeoDatabase exposes `ProgramSetExercise.IsOptional`; LeoCore exposes the trailing optional `SetExerciseDetails.IsOptional` parameter. Restart running .NET processes after updating their binaries.

### Automatic saving and incomplete drafts

The editor saves valid changes after an 800 ms pause. A compact toolbar icon shows saved, saving, pending, incomplete, connection-error or save-error status, with localized hover text and screen-reader announcements. There is no manual Save button. `lib/programs/autosave.ts` projects a saveable graph using the same validation as the API: incomplete new objects and their new descendants wait locally, while invalid existing objects keep their last saved version in the submitted graph. Other valid changes can still save. Completing an object schedules it automatically. A blank name on a new program waits; clearing an existing name retains the stored name until a valid replacement is entered. Pending changes are visibly marked, and incomplete local edits are not persisted across reloads.

`use-program-autosave.ts` serializes writes, queues the latest draft after an in-flight save, avoids duplicate creates and idle retries, and retains revision-based conflict protection. Failed snapshots wait for another edit; connection failures also retry when the browser comes back online; requests time out after 20 seconds. Saving updates the URL once without a route refresh. Program navigation disables prefetching to avoid hover-triggered loads of authenticated editor routes. Leaving the editor cancels scheduled saves; already submitted transactions may still finish.

## Workout editor (local draft)

`/[locale]/workouts` opens a single-day workout editor, reachable through the Workouts navigation tab. There is no canvas, zoom or free positioning: groups stack in the day, exercises stack within groups, and performed sets appear as compact objects under each exercise. The palette contains Group, Exercise and Set; drag or click to add. Grips reorder exercises/sets, including moving sets between exercises. Focus a grip and use up/down arrows for keyboard reordering. The options panel edits day title, scheduled date/time and notes, selects a catalog exercise, or edits a set's result/unit, additional weight/unit, duration and RIR. Its exercise selector also supports moving a set to another exercise. Removing a nonempty exercise asks for confirmation.

`components/workouts/workout-editor.tsx` owns local state. The page reads the existing localized exercise catalog for the shared searchable picker. It creates no workout API endpoints, schema changes or database writes. Drafts intentionally reset on navigation/reload and are visibly marked as local. The layout adapts to mobile with the palette above the day and options below. All five locales are supported.

Workout draft actions include Copy, Paste, Duplicate and Remove in the toolbar, plus per-row copy/remove icons. Ctrl/Cmd+C, V and D operate on the selected exercise (with its sets) or individual set; Delete removes it. Text inputs and the exercise-picker dialog retain their normal keyboard behavior. Clipboard snapshots use fresh IDs on paste, remain usable after deleting the source, and never share editable set objects.

The Number of sets control appears only at the top of set options (1–100), updating immediately. Repeated sets display as one compact set object with an ×N badge. Each exercise still owns a flat array of physical rows with unique IDs; client-only batchId metadata groups identical rows for display. Editing a compact object's fields updates its member rows. Increasing its count appends independent rows to that batch, decreasing retains its first rows, and other set objects are unchanged. Exercise headers show the total physical set count. Copy/paste, duplicate, delete, reordering and moves between exercises act on complete batches, with fresh row and batch IDs for copies. Future persistence remains one workout_set_exercises row per physical entry; no database changes were introduced.

Workout drafts prefill the scheduled date/time with now in the profile timezone, falling back to the browser timezone. The suggested title uses the account's primary language (`user_settings.language`), or the page language when unavailable, with a localized long date (for example, “Workout from 22 November 2026”). It follows edits to the scheduled date until the user edits the title. Reading preferences does not write profile or workout data. Browser timezone hydration uses a fixed server-provided instant to avoid date mismatches.

Workout groups support editable names and positive repeat counts, pointer/keyboard reordering and copying/duplicating/deleting complete branches. Exercise options include a Group selector, and exercises can be dragged between groups. Exercise drops require a group; starting through Add exercise creates a default group if needed. Sets in an empty selected group cannot accidentally attach to another group's exercise. Group copies regenerate all group/exercise/physical-set IDs while preserving compact set quantities and results. These are local draft changes only, with no schema updates or workout database writes.

### Workout from a saved program

The workout toolbar's From program dialog lists the signed-in user's saved programs. Select a program and a day (nested cycles appear in the day label), and use the day (the required minimum set count is imported). Replacing a nonempty structure asks for confirmation. The scheduled date, title and notes are retained. The imported local draft carries the program and normalized program-day ID for future persistence; no workout or schema writes occur.

`GET /api/programs/[id]/workout-template` is authenticated, owner-scoped and private/no-store. `loadProgramForWorkout` reads the canonical graph and day IDs in a repeatable-read, read-only transaction. The modal fetches only the selected program, cancels obsolete requests and handles loading/failure/empty states. Anonymous users see a sign-in hint.

`lib/workouts/program-template.ts` converts one day into fresh local groups, exercises and physical set rows. Group names/repeats, catalog assignments, compact quantities and target ranges are preserved. Set ranges use the required minimum; optional sets are not imported. Exercises without prescribed targets receive one blank set, while optional-only targets are omitted unless selected. Actual results, weights, elapsed time and RIR always begin empty; original prescriptions appear as guidance and matching-unit placeholders. Percent-of-1RM targets are displayed without inventing absolute weights. Filling results or changing the draft never edits the program.

The From program popup uses the same card grid as the exercise picker: accent-insensitive search, 12-item pages and keyboard-accessible card buttons. Selecting a program opens searchable, paginated day cards grouped under their cycle paths, with cycle descriptions/repeat counts and compact exercise prescriptions (sets × reps, load ranges, distance or duration). Search matches exercise names as well as cycle/day names; Back to programs preserves the program search. A failed load offers Try again, and template requests are bounded to 30 seconds. Day import uses required sets only; no subscription logic was added.

Workout export is available from the toolbar: TXT, Excel (.xlsx), and clipboard. Text starts with #nickname and dd.mm.yyyy using the scheduled local date. Consecutive sets with identical actual values, units, weight, time and RIR are compacted as reps × set count (e.g. 15 60kg, 10×2 80kg RIR 2); order is preserved. Missing results use — and planned targets are never substituted. Excel includes a compact summary plus one row per physical set on the Sets sheet, with group repeat counts retained as metadata. Exporting does not persist workouts or change programs.
